# Helper image materializer organization review

Reviewed the production ownership and organization separately from the test seam authored by this reviewer. No P2-or-higher production organization finding remains in the inspected change. Execution validation is pending the root agent's platform runs; this is a source review, not a build result.

`HelperImage` remains the owner of the private directory and immutable staged executable. It validates optional bundled bytes, selects a private path, delegates materialization, and cleans the owned path on failure or drop. The new `image_materialize` module owns the fork/write/reap lifecycle. The backend API documents host reaping and atfork assumptions rather than exposing process-internal machinery through domain types.

The writer descriptor originates only in the owned child. The child has immutable pre-fork path/byte storage, blocks inherited signal handlers, performs raw open/write/fchmod/close operations, and exits without Rust destructors. The parent saves fork errno before mask restoration and reaps a successfully forked child before reporting a mask-restoration failure. Interrupted wait calls retry; traced stops retain child ownership until a terminal status. These responsibilities form one bounded module and do not duplicate backend scheduling ownership.

The parent owns staged-path cleanup, while child exit owns descriptor cleanup on write and chmod failures. Keeping those separate reflects the process boundary. There is no additional public abstraction or generic process framework. A portable domain error is produced at the infrastructure boundary. Existing host requirements (exclusive child reaping, stable SIGCHLD behavior, platform atfork behavior) remain explicit practical limits.

The test-only synchronization is in `image_materialize_hook.rs`, compiled out of production. Its hook follows the actual writable open, and callbacks execute only in the original process; the child uses a bounded raw socket handshake. Parent callback panics release and reap the writer before propagating. A direct parent-writer mutation executes the same actual-open hook in its parent branch, so the regression cannot pass simply because observation precedes file creation. The public constructor fixture remains responsible for concurrent fork/exec behavior; a separate fixture checks bytes, permissions, non-overwrite, missing parents, and calling-thread signal masks. These test changes require independent correctness review because this reviewer authored them.

All touched production modules and new test modules remain under the repository's 350-nonblank-line limit. No frozen release-candidate source or native terminal parser code was changed for this follow-up.
