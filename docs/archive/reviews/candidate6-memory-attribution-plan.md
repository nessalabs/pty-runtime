## Minimum derivation after completed trials are available

1. Read only finalized JSONL with a successful full-duration `trial_result`, preserving hashes and failures separately. Validate the frozen source/binary/configuration and reconcile the final summary. Use the raw idle/resource cases for the ADR no-projection/no-payload objective; keep projected cases in a separate model-cost table.
2. For every raw population (1, 32, 64, 128) and repeat, extract `runtime`, `ready`, `measurement_start`, `measurement_end`, and `closed` checkpoint fields; corresponding budgets; physical owner/helper/fixture costs; and exact reader gauges. Retain null as unavailable. Confirm no output/queued input or optional projection, expected reader count and unchanged scratch capacity through the chosen idle interval. Record every discrepancy rather than substituting `N × read_chunk`.
3. Calculate `residual = H_idle − H_runtime − (S_idle − S_runtime)`, with `H` the requested Rust live heap and `S` actual scratch bytes. Report per-population medians/ranges and all individual values. Prefer the ready state for the cleanest no-phase-bookkeeping comparison, but retain later values as sensitivity evidence. Do not subtract quota limits, native reservations, estimated thread sizes, or RSS from requested heap.
4. Report the measured shared baseline **with its configured capacity**. `Population::new` creates the runtime and reserves `children` before the runtime checkpoint; that vector is already in the baseline. Shared runtime reservations also depend on `max_sessions = N + 1`. Do not subtract the child vector twice, count a capacity-dependent baseline as universal fixed overhead, or hide it by reporting only a per-session difference. Observer-container and other incremental fixture allocations can conservatively remain charged in the residual unless separately identified.
5. Close the remaining ownership proof: show that baseline allocations retained in `H_runtime` remain owned at the selected idle checkpoint, or bound baseline deallocations and add them back. A net heap delta can hide new control allocations when unrelated baseline allocations are released. With a proven baseline-release bound `F`, a conservative incremental control bound can use `residual + F` while retaining all unclassified positive fixture/shared growth. An exact allocation classification would be an alternative; `size_of` estimates alone are not ownership evidence.
6. Establish a settled snapshot argument. Gauges now record actual `Vec<u8>::capacity()` after allocation and release via RAII, closing the earlier [candidate-3 configured-scratch gap](idle-control-memory-assessment.md). They and allocator totals are separate relaxed reads, not an atomic allocation ledger. `report::checkpoint` obtains gauges, constructs formatting strings, then reads allocator totals. Stable expected reader/scratch counts over the idle interval support the subtraction, but source/lifecycle review or an explicit quiescent allocation boundary must rule out intervening release/replacement before asserting an exact upper bound. The control-socket readiness handshake alone is not that boundary.

The existing source and full completed matrix may support steps 1–4 without a new run. They may also supply a bounded ownership argument for steps 5–6, but this review has not established it. If they cannot, a narrowly scoped allocation-class/quiescence measurement is needed later; no change to the running collector is proposed.

## Reader stacks require separate attribution

The frozen `ProcessLimits` default requests `128 × 1024` bytes for each reader; `registration.rs` passes that request to `thread::Builder::stack_size`. Source configuration can report `N × requested_stack_bytes` as a **requested budget only**. It does not prove actual OS mapping size, guard regions, resident pages, peak usage, or stack safety. The load fixture does not override this production reader request. Fixture child thread stacks and shared owner worker stacks remain separate costs.

The current Darwin collector calls `ps` for PID/RSS/CPU, `lsof` for FDs and `ps -M` for thread counts. It records no virtual-size field, stack mapping, per-thread identity/address extent, residency split or committed-stack metric; PSS is explicitly unavailable. The Linux path reads only Rss/Pss from `smaps_rollup`, also losing per-mapping attribution. Neither path can distinguish stack memory from other owner memory after the fact. RSS changes include heap, allocator behavior and other mappings, so subtracting Rust requested bytes or multiplying thread counts is not a physical-stack measurement.

The minimum separate measurement would identify each reader's actual stack extent and correlate those extents with platform memory-map accounting while the same idle population is stable. Report usable reserved virtual bytes and guard space separately, then the platform's resident/private-dirty or committed measure with its exact definition and unavailable fields explicit. Reader stacks must be distinguished from shared worker/main stacks and workload-child stacks. The collector's aggregate PID/threads/RSS records are insufficient for this correlation. This is memory accounting work to schedule separately if authorized, not native fault investigation and not an additional workload performed here.

## Scoped handoff

The later 95-trial analysis should separate: measured capacity-dependent shared Rust baseline; conservative incremental raw heap/control residual; actual reader scratch; requested reader stack budget; **unmeasured physical stack attribution**; projected-model costs; owner RSS/PSS availability; helpers/children; and kernel/allocator costs not independently attributed. The current collector measures neither kernel PTY cost nor allocator overhead as isolated categories. Do not manufacture them as residuals from incompatible totals.

The ≤4 KiB claim remains pending the ownership/quiescence argument, and the ADR requirement to report reserved versus resident/committed stacks remains pending a separate measurement. These are evidence gaps, not demonstrated regressions. The completed first trial's low CPU and exact scratch count do not close either gap.
