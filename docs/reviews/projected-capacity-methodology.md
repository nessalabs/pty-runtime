# Projected saturation latency: reference acceptance and bounded capacity

Read-only methodology/DDD assessment of ADR 0002 and **completed candidate-4 projected capacity trial 1 only**. The active directory and frozen evidence were not modified; no active trial files, builds, workloads, Linux or native-crash work were used. Selected recorded facts and the completed-file hash are preserved at `docs/verification/projected-capacity-methodology/completed-trial-1.json`. The reviewer authored the earlier generic capacity fixture; this is a methodology assessment, not an independent implementation verdict on that fixture.

## Recorded result and interpretation

Trial 1 ran 64 resident/16 unpaced projected producers for 60 seconds after 10-second warmup, accepted 3,894,526,707 bytes over a 60.006605-second producer window (64,901,634 B/s, about 61.9 MiB/s). It completed exact byte/query/resource accounting, with zero ledger gap bytes. ProjectedOutput p99 was **80.9 ms versus the recorded 20 ms reference**, with p50 65.9 ms; the target record is false and trial `latency_targets_passed` is false. RawOutput p99 was 0.8 ms, InputDispatch 1.0 ms, ResizeDispatch 82.0 ms versus 100 ms, and CancelDispatch 3.602 ms versus 100 ms. All those boundary records report zero failed/unavailable samples. Fixture RTT p99 was 58.9 ms and max 76.417 ms; it remains a separate interval without an invented absolute SLA. One trial does not fulfill the five-repeat requirement.

**Preserve every failed target and all raw measurements.** This result cannot be called a 20 ms output-latency pass or evidence that peak projected throughput meets the reference latency. It is also not automatically proof that the mandated controlled-reference release workload fails.

ADR 0002 lines 197–205 specify the 64/16 combined **10 MiB/s** workload and explicitly retain it as the latency reference, then require rate/population sweeps to locate capacity and fairness limits. Lines 224–225 identify backpressured writes as a separate scenario requiring bounded admission and responsive cancellation. Lines 227–232 require five full repeats, reviewed host baselines and review of repeatable >10% throughput/p99 regressions. Reading the target table as an unlimited-offered-load SLA would erase the distinction between reference qualification and locating a capacity limit. The table itself does not explicitly enumerate target applicability by every future sweep, so record this scope interpretation before a readiness claim; do not silently rewrite target events or change the numerical threshold after a failing run.

Recommended disposition: record this as **correctness-complete saturation evidence with a failed 20 ms reference comparison at that operating point**. Keep overall machine-reported target failure unchanged. Require the controlled attached/detached/dominant 10 MiB/s cases to satisfy their reference thresholds across the required repeats; retain bounded-state, cleanup, fairness and responsive-control requirements under saturation. Saturated resize/cancel failures or starvation/incorrect accounting would remain actionable overload defects. A regression requires a comparable reviewed same-host/same-configuration baseline; a first newly added saturation point alone does not establish a >10% regression. Neither this interpretation nor one completed trial establishes overall release readiness.

## Fixture-only staging-slot sweep

Recommend adding an explicit **fixture configuration** for per-session `ProjectionOptions::staging_slots`, with named projected-capacity cases at **32, 64, 128 and the unchanged 256 default**. Apply it through the existing public SessionOptions projection field before spawn. Validate a finite positive value through the existing domain contract and include the actual value in configuration/source identity. Leave product defaults, request_slots, staging_bytes, global projection limits, producer chunk/rate, population, native/grid limits, observer work and control cadence fixed. Raw/transient sessions have no projection; reject or explicitly mark the parameter inapplicable rather than presenting a raw result as a parser-slot effect. This is normal composition of public policy choices; it requires no new domain abstraction or infrastructure coupling.

Keep the current five 256-slot trials as the reference for this sweep. Any full qualifying comparison needs five post-warmup 60-second repeats at each chosen point, with the same host and competing-load record; shorter pilots are exploratory only. Pair the most promising reduced-slot configuration with the unchanged controlled 10 MiB/s reference. If the decision needs the highest rate that still meets 20 ms, use controlled offered-rate points around the observed transition instead of treating an unpaced producer's zero offered-rate sentinel as a rate measurement. Preserve every rejected, censored, failed and incomplete run.

Why this sweep is motivated: trial 1 accepted about 1023.5 bytes per ProjectedOutput sample, despite 4093-byte producer write requests. Assuming evenly shared active throughput and a near-full local queue, `256 × 1023.5 B / (64.9 MB/s ÷ 16)` is about **64.6 ms**, near the observed 65.9 ms p50. This is a queueing hypothesis, not measured occupancy or proof of causation; using producer chunk size would overestimate queue residence. Smaller queues should be evaluated empirically, not assumed to meet p99 or preserve throughput. At 128 active sessions the existing shared cap can become binding differently, so 64/16 results do not establish the 128-session result.

Measure accepted throughput and per-producer fairness together with ProjectedOutput/RawOutput/InputDispatch/Resize/Cancel distributions, sample counts, fixture RTT, producer EAGAIN/POLLOUT wait totals and quotas/cleanup. Reducing staging can move waiting upstream into PTY/kernel/producer backpressure before the host-read timestamp, so a lower internal ProjectedOutput p99 alone does not establish lower end-to-end latency. Retain fixture RTT and writer-wait evidence to make that tradeoff visible. The recommendation is to qualify the queue-depth tradeoff first; it is **not a recommendation to change the product default on one saturation result**.
