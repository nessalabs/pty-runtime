## P2: final capped write can evade censor detection — resolved

In `producer.rs`, `capped` is set only at the top of the outer deadline-controlled loop. A successful final write can increase `result.bytes` to `plan.cap`, after which the deadline expires before the next outer iteration. `run` returns `capped=false`; `phase.rs` relies on that flag, so the capacity trial can pass despite exhausting its finite byte allowance. The author now derives `result.capped = result.bytes == plan.cap` immediately before the successful return, independent of which deadline check ends the loop. Independent source inspection confirms this closes the false-success path. Pre-fix source is retained in `docs/verification/load-capacity/cap-boundary/producer-before.rs.txt`. At the coordinating task’s explicit direction, no clock/write abstraction was introduced solely to force this scheduler boundary; this is a statically demonstrated defect, without a deterministic failing race execution. Existing real-socket tests prove exact capped output and bounded stalled-output accounting and pass after the fix. This evidence is not presented as a new behavioral red/green regression.
